## 零、一句话

它最值钱的不是代码，是**它把「她要不要开口」拆成了四个不同动作，并且让机器只给建议不给命令**。

而这个设计**只存在于它的收尾层**（`conversation-closure`），主动开口层（`purpose`）仍然是机器选一个目标再叫醒她——
同一个项目里两种哲学并存。**我们要做的是把收尾层那个形状，搬到开口层。**

## 一、直接改设计（哲学层，最值钱）

### 1.1 收尾判断：只给参数＋建议，不替她决定

`src/conversation-closure.js:155` `assessConversationClosure()` 输出：

- `verdict`：`continue` / `linger` / `close`
- `score`（0~1）＋`signals`（六项数值）＋`reasons[]`＋`advice`

六项信号（`docs/guides/CONVERSATION_CLOSURE.md §1`）：

| 信号 | 含义 |
| --- | --- |
| 我最后一句 | 收尾式（嗯/好/晚安）／提问在等答案／实质内容还在输出 |
| 对方最后一句 | ending / question / request / ack / substantive 五类 |
| 我的继续意愿 `ownIntent` | pendingThoughts ＋ 待追问话题 ＋ 自己最后一句是提问 |
| 对方的继续意愿 `theirIntent` | 最后一句性质 ＋ @/引用 ＋ 近 5 分钟条数 |
| 话题闭环 `topicClosure` | 说定了 / 双方都在收 / 还在问 |
| 节奏疲劳 `fatigue` | 近 10 分钟条数、近 3 条平均长度、静默时长 |

代码注释写死（`:392` `closurePromptBlock`）：

> 只给「参数 + 建议」，不替模型做决定。

文档同句（`CONVERSATION_CLOSURE.md §1`末）：

> **代码只给建议。** 最终收不收由模型调用 `qq_close_conversation` 决定。

**为什么这条最值钱**：这就是 realheart 每轮注入该有的形状——机器把算得出的事实摆到她面前，决定权留给她。
我们现在注入的是「心情是什么」，缺的是「现在这段该不该继续」。

### 1.2 `closeGate`：把「不想说」和「在躲」分开

`src/conversation-closure.js:511`：

```js
/**
 * 收尾前的人性化硬闸：对方明确在提问/求助、且我还没接时，不接受「结束」。
 * 这不是不信任模型，而是把「不想回」和「逃避」分开：前者可以收尾，后者必须先答。
 */
```

- 触发条件：`awaitingTheirAnswer` = 对方最后一句是 question/request 且我没接
- 行为：`blocked: true, reason: 'open-question'`，配一句给模型的改口指引
- 配置 `requireNoOpenQuestion` 默认 `true`，文档明说「关掉它等于允许『用结束逃避』，不建议」

**对 realheart 直接可用**：`rh_control` 让她能停，但缺一个「停之前先看有没有该接的话」。
自由不是可以赖掉。这条把两者分开了。

### 1.3 四个动作拆开，沉默分四种形态

`docs/guides/CONVERSATION_CLOSURE.md §2`：

| 动作 | 语义 | 改唤醒配置 | 要沉睡前观察 | 留结束点 |
| --- | --- | --- | --- | --- |
| `qq_send_message` | 说话 | 否 | 否 | 否 |
| `qq_mark_read` | 看过了，划走 | 否 | 是（若当前是潜水配置） | 否 |
| `qq_set_wake_config` | 进入潜水 | **是** | 是 | 否 |
| `qq_close_conversation` | 这段自然结束 | 否 | 否 | **是**（summary / nextOpening） |

关键点三句：

1. **`close` 不是潜水**：唤醒配置原样保留，对方再找、开新话题、私聊都会照常醒。它只是「这一轮不再输出」。
2. **冷却只压软唤醒**：`cooldownMs` 默认 20 分钟，只跳过 `probability` / `replyCheck` / `proactiveCheck`；
   **不压** `atMention` / `nameMention` / `question` / `keyword` / `poke` / `speaker` / `private`。
   代码里就是 `SOFT_WAKE_REASONS` 一个集合（`:491`）。
3. 文档原句：**结束不是把人关掉。**

### 1.4 结束点要留东西，重开要能认出是新的开始

结束记录落会话状态（`CONVERSATION_CLOSURE.md §4`）：

```json
"closure": {
  "at": 1761280000000, "kind": "private", "reason": "natural",
  "summary": "聊到扯平这件事",
  "nextOpening": "问问她周末去不去看展",
  "cooldownUntil": 1761281200000,
  "lastOtherKind": "substantive", "lastSelfKind": "ack",
  "reopenedAt": 0, "reopenReason": ""
}
```

- `reason` 枚举：`natural / topic-done / explicit-end / busy / tired / other`
- `summary` / `nextOpening` 截断上限 160 / 120 字（配置可调）
- 重开：私聊对方一开口就算新开始；群聊只有直接叫到/引用/提问/道别才重开，普通闲聊不打断冷却
- 重开后 10 分钟内注入一句「上次这段刚收过尾，现在是新的开始，**别复读上次的结尾**」

## 二、可直接照搬的机制

### 2.1 回执四态（`PITFALLS #58` ＋ `PURPOSE_OUTREACH §1`）

- 回合结果分 `sent` / `silent` / `failed` / `interrupted`
- **不能用 `session.prompt` 的返回值当回执**：DSH 的 `sessionPromptValueSchema` 里 `command` 槽只在 slash command 派发时出现，普通 prompt 返回 `{accepted:true}` 就结束
- 真回执 = 事件流 `turn/end` 的 `ended.text` ＋ `recordSentMessagesV2` / `sendToolSucceeded`
- `silent` 的判据 = 回合正常结束但没发（她在内部备忘里写【状态】跳过，或没找到想说的）

我们现在的判据是「对方真回了一句才算送到」，方向对，但缺 `failed` 和 `interrupted` 两态。

### 2.2 tick 重算，不押一次性定时器（`#58`）

- `nextFireAt` 落盘，60 秒 tick 每次重算「现在该不该出发」
- 重启时把在途回合记 `interrupted`，等一个初始延迟再来，**不补发**（否则重启后连发好几条）
- 理由写死：桥接重启、系统时钟跳变、DSH 掉线重连都会让 `setTimeout` 失效；它自己的早安问候就因此丢过 08:00（`#41`）

自由时间那套必须照做。

### 2.3 目标假设 ＋ 观察账本（`#60`、`purpose-engine.js:1026-1230`）

**归属四分**（`GOAL_OWNERS`）：`self` / `owner` / `member` / `media`

规则：一个事件 → 1~3 个候选目标；「群友想玩」先记成 `member` 的目标，**重复出现 / 直接点她 / 过去有同类兴趣**才升级成 `self`。

**目标状态机**（`GOAL_STATUSES`）：

```
hypothesis → active → confirmed / rejected → done / expired
```

字段：`confidence` / `value` / `urgency` / `risk` / `action` / `nextStep` / `evidence`（最多 4 条）/ `attempts` / `sightings` / `expiresAt`（默认 TTL 7 天）

**验证反馈**（`:1024` 注释）：

> 用户反馈（主人回复）会更新置信度/状态，而不是让一个猜测永久变成欲望。

**观察账本**（`updateObservations`，`:1087`）：

- key = `domain|对象名小写`
- 记 `count` / `firstAt` / `lastAt` / `subjects[]` / `positive` / `negative` / `seenIds`
- 30 天窗口，最多 80 条
- 注释：**跨轮保留，用来压「一次视频=永久欲望」**

**对 realheart 的用法**：心情账本的 `why_ref` 现在只要求「指得出事件」，没要求「这个事件属于谁」。
加一个 owner 字段，「因为他说的我难过」和「我自己想到这个就难过」就能分开了。
观察账本还能给「同一件事被提了三次」一个落点——那比单次事件重。

### 2.4 衰减的工程细节（`MEMORY_CARD.md §5`）

四档清晰度（**每天最多降一档**，所以是慢慢模糊不是一次性删）：

```
vivid → clear → fuzzy → trace → 遗忘（记录删除）
```

能直接抄的纯工程四条：

1. **补跑**：DSH 关了好几天，下次整理按错过天数连续降档（**最多 30 天**）—— 停机不停止遗忘
2. **遗忘 = 删除正文**，只保留 `stats.forgotten` 计数，不把「已忘」的内容继续喂给模型
3. **归档必须在衰减之前**：`archiveDecayedToFull()` 先 append 到全量卡，写成功后才写 `fullArchivedAt`（避免「标记了但没写进去」）
4. **豁免档**：主人相关且重要度 ≥65 的永不遗忘，最差保持「清楚」；「最初」标记同理，也不参与容量淘汰

容量告警 80% / 90% / 100%，写盘用原子写（临时文件 + rename），每日整理前备份衰减卡。

⚠️ **别抄它的衰减输入**。它的 `targetClarity()` 按「重要度 ＋ 天数」算，那是**时间驱动的物理衰减**。
realheart 的 `decayed` 要有事件依据（你那份状态层第二稿已经定了 τ 只在 `decayed` 上算），
否则就变成「时间让心情淡」，跟「心情必须有来处」直接打架。**抄节奏和补跑，别抄公式。**

### 2.5 注入预算：新增小节必须回答「先砍谁」（`#70`）

原坑：桌宠记忆小节 priority 定成 23，预算一紧就先被裁，单测只建几条记录覆盖不到真实压力，
表现是「记录在库里却永远不出现」。

它的处置两条：

1. priority 排到区间里（提到 36，高于 recent 30、低于 owner 40），限制 4 条
2. 补一条**预算压力测试**：30 条主人记忆 + 20 条群消息 + 1 条桌宠，`maxChars=900` 时必须仍出现

教训原句：

> 新增提示词小节必须回答「预算不够时先砍谁」，并用真实量级的卡做回归；只测「记录少时能渲染出来」等于没测。

realheart 每轮注入几十到几百字，这条现在就站在门口。

### 2.6 事件游标 bootId（`#67`）

- 现象：插件重启后 `eventSeq` 从 1 重来，客户端还带旧 `since=12` 轮询，`id > 12` 永远为空 → **既不报错也不返回**
- 修法两边都要：服务端 `since > eventSeq` 视为旧 boot，直接回当前水位；客户端 `bootId` 一变就设 `needsBaseline`，下一轮用不带 since 的请求重取
- 回归测试钉住 `poll({since: 99})` 返回当前水位而不是死等

realheart 每轮注入靠 session 事件，有同一个风险，而且这个坑的形状是**静默失效**。

## 三、工程习惯（不用全抄，挑三条）

### 3.1 五层工具闸门＋失败码语义（`AGENT-TOOLS-AND-PRESETS.md §3`）

```
① 进程/传输：只有装进 profile 的 server 才存在
② 工具是否注册：配置 false 时该工具压根不在 schema 里
③ 调用方身份：x-agent-call + x-agent-token 必须命中一个活跃会话；
              漏传令牌不会升级成管理端全权（防 confused deputy）
④ 运行状态：暂停 / 总开关 / 该会话是否在当前模式允许范围
⑤ 业务闸门：白名单、敏感信息、长度条数、频率、token 额度
```

比 realheart 现在「有工具/没工具」二分细。特别是第②层：**不放行不是报错，是不在 schema 里**。

### 3.2 「保存」和「生效」脱节（`#62`）

三个真因都不是 UI 问题：

1. 一处读配置（插件 `apply()` 里直接启动，没有「是否启用」的读取点）
2. 三份真相（`bridge.autoStart` / 启动按钮 / 自愈轮询各读各的，必然漂移）
3. 开关只写文件、不执行副作用

`rh_control` 如果只写文件不管生命周期，会撞同一个。判据：**开关必须有唯一读取点 ＋ 副作用立刻发生**。

### 3.3 「为什么没说话」也要落盘（`#32`）

原坑：鱼群保护只写活动日志，页面看不到「刚才为什么没说话」；重启后连冷却都丢了（字段不在 `saveSocialV2State` 的保存列表里）。

修法：每轮触发追加一条 `{at, reason, 各项证据数, until}`，每群最多 30 条；加载/保存都纳入状态。

我们的观测页方向对，差的只是「判定依据」也入账。

## 四、明确不用（抄了就变味）

### 4.1 打分表

`minePurposeSeeds`（`purpose-engine.js:1677`）＋ `selectPurpose`（`:1803`）：

```
score = 需求向量·(0.35+驱动) + 自我相关 0.35 + 主人相关 0.30
      + 情绪强度 0.15 + 高唤醒 0.10 + 未解决 0.20
      + 重复/社会证明 0.30 + 新鲜度 0.20 + 时间衰减 0.10
```

你在状态层第二稿写明不做：情绪分 / 加权求和 / 心情指数；
以及那句最硬的——**「一旦用来决定『我该多说还是少说』，它就从描述变成了操纵」**。

surfcore 正是拿这个分数决定要不要叫醒她。**这是架构互斥，不是程度差异。**

### 4.2 定时驱动当动机

60 秒 tick 是**抗重启的手段**（2.2），不是目的来源。拿 tick 当动机就是打卡式主动。

### 4.3 14 标签设置页 ＋ 39 工具面

那是「给用户调」的规模，不是「她有状态」的规模。realheart 现在四个工具正好。

## 五、修正我上轮说错的地方

上轮我说：「它的 silent 是这一轮的失败产物，不是主动的决定；它没有『什么都没想』这个合法状态。」

**这句话只对 `purpose` 那层成立，对整个项目是错的。**

只是那套在 PKG 的另一层，我上轮只读了 PURPOSE 文档。

**改后的判断**：surfcore 不是「全调度」，是**分层**——主动开口层机器决定，收尾层她决定。
所以 realheart 不是要推翻它，是要**把收尾层那个形状（判断给建议、决定留给她、硬闸只拦逃避）搬到开口层**。
